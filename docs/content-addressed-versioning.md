# Content-Addressed Versioning: Chains, Scopes, Epochs and Deltas

Status: design, 2026-10-29. This extends the [control-plane persistence algebra](control-plane-persistence-algebra.md), whose vocabulary (entity, version, edge, epoch) it assumes, and it is not implemented: the `control-plane` crate still models a version's predecessor by id order and stores every version as a full payload. It was worked out against two consumers, one whose instances carry single-writer generation chains and pin a config epoch, and one with a git-resident metadata repository fed by a delta pipeline from devices. Where those consumers already solved a piece of the problem, the solution is described here in general terms rather than cited.

The argument in one paragraph: give every version an explicit parent, treat that parent pointer as an ordinary pinned entity reference whose target happens to be the same entity, and most of what follows is forced. Branching, deltas, content addressing, the epoch log and history truncation all become properties of one edge type with three resolver scopes, rather than five mechanisms.

## 1. The parent edge

Today a version's predecessor is implied by `versionId` order. The store therefore cannot tell a version written knowing the current head from one written concurrently against an older one; the two serialize by id and the second silently discards the first's update. That is the lost-update problem, and it is present now, with opaque payloads, before any of the rest of this document applies.

An explicit parent edge makes it visible. The edge is a nullable composite foreign key `(entityId, parentVersionId)`, null for a root, which is the same shape the pinned/floating edge already uses. The fix for lost updates is then one write-time rule, which is that the parent must equal the current head or the insert is refused. That is optimistic concurrency for the cost of a column.

The same edge is what per-property deltas need in order to be well defined at all, since a delta is relative to a named parent rather than to whatever happened to sort before it. And it is, unavoidably, what branching is: lift the one-head rule and two children of one parent are a fork, "latest" becomes "head of a named ref", and a merge is a version with two parents, automatic where the operations commute (§9) and a policy question where they do not. The pressure for branching comes from the evolution side of consumers, proposals, experiments and legs, and not from the data plane, which stays linear by construction wherever an instance has a single writer. The edge can therefore go in now with the one-head rule kept, and branching becomes a rule relaxed later rather than a schema migrated to.

Three costs have to be settled before the edge goes in, and each is taken up below. Referential integrity alone can never reclaim a chain, because every child references its parent, so garbage collection has to become reachability from live epochs and heads (§4). A read that folds deltas walks the chain back to the last full replace, so the replace cadence becomes a read-cost knob (§9). And content addressing wants the parent hash inside the version hash, Merkle style, which makes this the natural moment to do the deferred identity work rather than retrofitting it after chains exist.

## 2. What consumers already have

Three pieces of existing consumer design bear on this and should be understood before any of it is built.

A git-resident metadata-repository design already has the chain for git-resident types, at commit granularity rather than per entity. A repo epoch is a commit hash, entities are monotonic frozen files inside it, branching and merging are git's own, and the merge gate re-validates. The per-entity parent edge is therefore needed by the RDBMS realm, the high-cardinality machine-written instances, and not by the git realm, which narrows the question considerably. That design also observed independently that its pinned-versus-floating references and this algebra's nullable composite foreign key converged on the same encoding, which is the encoding the parent edge reuses.

A device agent's batch layer in the same consumer is a single-writer delta chain with the invariant worth copying: every batch carries the hash of the full post-application state although it ships only the delta, both ends compute it, and a mismatch forces a rotation to a full snapshot. A version here should carry its materialized full-state hash in the same way. That one field is the Merkle identity, the divergence check for concurrent writers, and the correctness check on a delta fold.

That consumer's wire-format delta codec, together with its keyed-recursion discipline, is the working prototype of the shared delta encoding §9 needs: schema-oblivious field-level diffs of protobuf wire bytes in canonical form for scalars, and a declared key per repeated message field for collections, degrading to whole-group replacement where no key is declared. Its documented limits, repeated fields replace as a group and maps are hostile, are the collection discipline arrived at from the other direction.

One tension should be carried over rather than rediscovered. The agent design records as open work that its set hash is defined over bytes the Merkle layer exists not to hold. A per-version full-state hash has the identical tension and should take the identical resolution, a subtree root standing in for the set hash on tree-shaped payloads.

## 3. One reference, three scopes

The chain pointer and the entity reference are one concept, and the chain pointer needs no new column: it is the edge whose target entity equals its source entity, a pinned self-reference, derivable from the endpoints the edge table already has. What differs is the resolver scope, and four behaviors hang off it.

Pinning. A dependency may float. A parent may not, because "the latest version of myself" is a cycle, so the self scope requires a non-null version.

Closure. Dependency edges are traversed when a closure is materialized. Self edges must be skipped, or every closure drags in the entity's whole history.

Liveness. Dependency edges keep their targets alive through the foreign-key delete gate. Self edges must not, or history is immortal. Liveness is reachability over non-self edges from epochs and heads, and how much history to keep is a separate retention policy (§4).

Truncation. Dropping old history is re-rooting: null the oldest retained version's parent, so that it becomes a root, and delete what lay behind it. This is git's shallow clone, and it is the one place the two halves of a reference legitimately part. A dependency's foreign key and content hash must never diverge, since a dangling dependency is a bug. A parent's foreign key may be nulled while its hash is kept as an attestation of what the truncated history was.

Acyclicity is free in the self scope, because a parent's version precedes its child's and, under content addressing, its hash is inside the child's. A merge with two parents keeps the property.

The three scopes, then, are `self` for history, `store` for dependencies, pinned or floating, inside the closure and liveness-conferring, and `realm` for referents outside the typed store, which §5 covers.

## 4. Garbage collection and retention

Referential integrity cannot reclaim a chain, so the delete gate the algebra relies on today is insufficient once parent edges exist. Liveness becomes reachability: a version is live if it is reachable over non-self edges from a live epoch or a named head. History behind a live version is governed by a retention policy, in versions or in time, applied by re-rooting as described in §3. The ledger's rule that an identity is never reissued is untouched, since truncation removes versions and never identities.

Realm roots (§5) are exactly the reverse references the cross-realm sweep in the metadata-repo design's garbage-collection protocol has to find before anything in git may be collected, so they want an index from the start.

## 5. Roots across realms

The deployment picture is an RDBMS full of deltas whose chains mostly point at versions in the same store and whose roots point up at git. It answers the metadata-repo design's residency-migration question (its §8): an entity that outgrows git keeps its history by reference rather than by copy, with the first database version's parent being the last git version. Three rules make it hold.

A root is always a full replace, never a delta. Otherwise a read folds across the realm boundary and git becomes a read dependency rather than provenance. This is the rule a device agent applies at a boot epoch and a single-writer instance applies at a new lifetime: a realm or epoch boundary is a replace point. Expressed as a constraint in §9, a null parent forces a null mutation set.

A realm root needs no scheme. Its parent is an earlier version of the same entity, and which realm held that version follows from the residency its Entity Type declared at that type version, so the pointer stays (id, version, hash). The scheme-qualified form of §6 is reserved for referents that are not entities at all.

At the root the two halves of the reference part in the way §3 describes. The parent foreign key is null, unless the git version has been hydrated into the store, in which case it is an ordinary self edge into the mirror rows. The parent hash is always kept.

Three kinds of root therefore share one shape, no parent anywhere, re-rooted by truncation, and parent in another realm, distinguished only by whether a hash is present and whether the ledger knows it. The schema does not need to tell them apart.

A single-writer instance store has the same topology one rung down. An instance's generation chain is a self-scope chain in the data-plane store, its root is the instance's creation, and its header pins a type version and a config epoch that are git-resident. The design for the control plane and the design for the instance store are the same design at different churn.

## 6. The textual form of a reference

A URL-shaped rendering whose scheme names the realm (`git://<commit>` for a repo epoch at rung 0 or 1, a bare or self-scheme form within the store) is attractive and collides with the metadata-repo rule that references name identities and never locations. The collision resolves if the scheme is an identity space rather than an address. A commit hash is content-addressed and needs no host, and the same-store form carries no scheme because the target's realm is already declared by its Entity Type's residency, which is where that design puts it. So a scheme is mandatory exactly when the referent is outside the typed store, a commit, a build manifest, rung 0, and forbidden otherwise.

The URL is the canonical text rendering of an `EntityRef` value, for humans, logs and diffs; `value.proto` already permits a `value#rev` string form. It is not a storage encoding, and rows keep typed columns so foreign keys still work. A parent edge prints both halves, the version id the foreign key enforces and the content hash only a reconciler can check, which is what makes the chain self-certifying.

## 7. The epoch as a version

The epoch, defined in the algebra as the fully pinned snapshot that resolves every floating reference across every entity type at one instant, needs no separate machinery once chains exist. It is an entity version of an `Epoch` type whose payload is the selection, entity to version with types included, and whose parent is the previous epoch. Everything the chain gives a version it then gives the epoch log.

The epoch head is the head of that entity's chain rather than a special mutable cell or `max(epochId)`. Epoch garbage collection is history truncation on that chain, under the re-rooting rule. A delta epoch, recording only the selections that changed since its parent and folding back to the last full one, is the structural-shared closure the first cut defers, arrived at as the ordinary replace-or-delta choice of §9. And the epoch's content hash is the Merkle root over everything reachable from it, which completes the git mapping properly: an epoch is a commit, its selection is a tree, an entity version is a blob, and the version chains are the per-path history git derives rather than stores.

Branching, when it comes, lives here and almost nowhere else. A staging epoch and a production epoch are two heads of the `Epoch` entity, named refs, and a version chain below only ever forks because two epochs on different heads selected different children of one parent.

The one rule to keep from the current design is that an epoch is cut at a publish boundary and never mid-publish, so a selection cannot straddle a multi-entity write. Referential integrity guarantees that what the epoch selects exists; cutting at the boundary guarantees that what it selects is coherent. A consumer's config epoch is this object exactly, pinned from an instance's header.

## 8. Cutting an epoch

Cutting an epoch has a serialization point but does not need a global read lock, and inside one store it does not strictly need a global write lock either. Three things suffice: a transaction snapshot, which MVCC gives without blocking writers because versions are append-only; publish atomicity, either one transaction per logical publish or a publish id with a completion marker so the cut selects only completed publishes as of its snapshot, which is a watermark rather than a lock; and a compare-and-swap on the `Epoch` entity's head under the one-head rule, which is the only mutable cell and the whole critical section.

It degrades to a barrier in two cases. Across realms no snapshot spans git and the database, so hydration of a repo epoch must itself be a publish, after which the cut sees git state as rows in its own snapshot and records both the commit and the snapshot. And a writer outside the publish protocol, the unfenced direct SQL writer the metadata-repo design already notes, can only be made coherent by a short pause of writers, which is the argument for fencing that writer rather than for pausing everyone.

A short global write lock (pause publishes, read every head, append the epoch, release) is nonetheless a correct and simpler implementation of the same cut, and the right first one while publishes and cuts are both rare. The snapshot-plus-watermark form is the upgrade for when either becomes frequent enough that one should not wait on the other. Where the store is a replicated log, as a consumer's config epochs may be, the log is the serialization point and the question does not arise.

## 9. Mutation modes without entity-attribute-value

Per-property deltas are the reason chains are worth having and the easiest way to ruin the version table. The way to have them without turning every version into an entity-attribute-value store is a side table that carries modes and never values.

The version row stays narrow (entity, version, parent, hashes, opaque payload) and gains one nullable foreign key, `mutations`. Null means this version replaces every value, which is the common case, the root case, and the only case the first cut has to implement; the invariant `parent IS NULL => mutations IS NULL` is §5's "a root is a full replace" expressed as a constraint. Non-null points at an ordered list of operations, rows `(mutations, seq, path, mode)`, with `path` a canonical navigation path, the same form the validation predicates already use to name a field, and `mode` one of replace, add, remove and clear. The table is a list of operations and not a slot per property: a version that changes one value four levels deep carries one row whose path is four segments long, and a version that touches nothing but that carries nothing else. The list is ordered because two operations may name the same path in one version, an add followed by a remove of the same key, and they apply in sequence; a writer may normalize to one operation per path before committing, but the store does not require it. Clear exists because proto3 presence cannot express "now absent" inside the payload itself, which is also why that codec lists cleared tags beside changed records.

A listed path's new content is in the payload. An unlisted path is inherited from the parent. A delta version's payload therefore contains only what its rows name, and materializing a version walks back to the nearest ancestor with a null `mutations` and applies its lists forward, so the replace cadence is the read-cost knob §1 promised.

What the rows buy over an opaque delta descriptor on the version is queryability: which versions touched a path is one index lookup, which is what the reconciler's bisect, analytics, and above all merge want. Merge becomes a join on the side table, and the join is on the prefix relation between paths rather than on equality, because a replace at `foo` and an add at `foo.bars[k]` are in conflict although their paths differ: two children of one parent conflict if and only if one side's path is a prefix of, or equal to, the other's and either side's mode is replace or clear; otherwise their rows union, with add and remove on keyed collections unioning element-wise inside the payload. Element identity for add and remove lives in the payload under the declared key per repeated field and never in the rows, which is what keeps the side table from growing a value column by accident.

Which operations commute is the line between what the algebra may merge on its own and what needs a policy. Adding elements to a keyed collection and removing them by identity are lattice joins, so concurrent versions merge without an order being chosen. Appending to an ordered array and deleting by index depend on a position only a serialized writer can fix, so they are refused at this layer and stay with the consumer that has one.

The same four modes cover maps, arrays with a declared key, and sets, because the mode names what happened and the payload names to what. On a map, add is put, insert or overwrite by key, with the entries in the payload; remove is delete by key, with the keys in the payload; replace and clear are the whole map. On an array whose element type declares a key, add and remove are by that key and the array behaves as a keyed collection; an array that declares no key admits only replace and clear, which is the whole-group replacement the delta codec already falls back to. A set is a keyed collection whose key is the whole element. Element identity is therefore intrinsic for maps, declared for arrays of structs, and trivial for sets, and in every case it lives in the payload and never in the rows.

Commutation is finer than the path for keyed collections, and the merge rule has to say so. Add on distinct keys commutes. Remove on any keys commutes. Add and add on the same key commute only if the values are equal, and otherwise conflict, since choosing between them needs an order. Add and remove on the same key conflict, and resolving that pair is the add-wins or remove-wins choice the observed-remove set literature makes explicit, which belongs to merge policy rather than to the algebra. So the side-table join decides conflict at path granularity, replace or clear against anything at or beneath it, and the payload join decides it at key granularity within a path that both sides touched with add or remove.

The surface syntax a consumer offers over this, the nano-DSL of `m.add(k, v)`, `m.deleteKeys(k1, k2)`, `m = {...}`, `a.append(x)`, `a.removeByKey(id)` and plain `s = v`, lowers to exactly these four node kinds. Write-once and append-only are not node kinds. They are disciplines declared on the slot, write-once admitting one set and no further, append-only admitting add and nothing else, immutable admitting nothing, and a node the slot does not admit is a registration-time rejection where the handler language is statically analyzable and a commit-time one where it is not.

A row naming a path whose slot is `mutable: false` (see `StructField.mutable` in `value.proto`) is a type-level violation the consumer's validator rejects, since the algebra does not read types. And the rows are exactly the mutation nodes the README TODO proposes a handler's assignment sugar should lower to: a handler emits set, clear, add and remove nodes, and a version's mutation list is their transcription in order.

## 10. Git-resident versions always replace

`mutations` is null for anything hydrated from a repo, and the side table is an RDBMS-realm structure only. This describes git-residency rather than restricting it. A published version in the metadata-repo design is a whole frozen file, human-authored and reviewed as a document, with git computing its own deltas in packfiles and its own diff view for the reviewer, so a delta representation inside the file would duplicate both and break the one-file-nothing-touches discipline.

Two consequences follow. Whether a type's versions may be deltas at all is decided by the residency its Entity Type declares, with no further flag, and a residency migration to the database is the moment deltas become available to an entity. And a realm boundary is a replace point on both sides, since the git parent is a full replace by this rule and the database root is one by §5, so hydration never folds and a chain's fold never leaves the store it started in.

Three git layouts are possible and only two are worth having. Frozen full copies, the current layout, cost a byte copy per publish and ask nothing of readers. Mutate-in-place, the TODO below, costs nothing per publish and asks readers to resolve history through the ledger and git. A root document plus per-version delta files (`root.yaml`, `v123/delta.yaml`) is worse than either and should not be reached for as a compromise: every reader folds by hand, git is already storing deltas underneath, and it would reintroduce into the git realm the mutation modes this section keeps out of it.

## 11. Open items

- **Mutate-in-place in git registries.** Allow the current document to be edited rather than archived to `foo/vN.yaml` first, once every client is known to read git history and can resolve a pinned `(id, version)` by walking commits. Preconditions: the ledger gains the commit hash that published each version, so resolution is a ledger lookup followed by a `git show` and never a search; the merge gate's byte-identical-archive check becomes a check that the ledger line and the committed blob hash agree; and the reconciler's git-side set hash is computed from ledger-named blobs rather than the working tree. Hydration is unaffected. The cost is that a shallow or partial clone can no longer resolve old versions, the same trade §3's re-rooting makes, which argues for a per-registry choice declared at rung 1 rather than a global switch.
- **Selector chaining for nested mutations.** A mutation such as "delete the third value from the array `bar`, a field of the struct `bars`, itself a field of `foo`" needs a path whose segments are a field name, a map key, a declared element key, or an index, chained to any depth. The side table's `path` column must be the validation predicates' navigation `Path`, extended with the collection selectors, rather than a second grammar; the JSONPath support already in the expression layer is the obvious surface syntax and should be checked for fit before anything is invented. Three rules to settle with it. An operation's path is the deepest segment touched, and every enclosing struct is implicitly modified in part, so the fold descends through ancestors without operations of their own. An index selector is legal only where the enclosing array declares no key and the writer is serialized, which is the ordered-array case §9 refuses at the algebra and permits in a single-writer consumer, so the two realms admit different selector sets and the type-level validator enforces which. And a selector through a map or keyed array is by key, never by position, so that the same path means the same slot on both sides of a merge. Concretely, `PathSeg` in `types/src/validation.rs` has `Field` and `Index` today, and `Index` on a map is defined as position in iteration order, which is fine for pointing at a violation and unusable as a mutation selector; a `Key` segment carrying a map key or a declared element key is the missing variant, and mutation paths must be forbidden from using `Index` on maps and keyed arrays at all.
- **The shared delta encoding.** A `CollectionDelta` form in `value.proto` for keyed collections, with `proto-delta` as the scalar half, and a declared element identity for arrays of structs that want set semantics.
- **Merge policy for non-commuting conflicts**, which is the part of branching that cannot be automated and should be designed when the first consumer needs a second head.
- **Retention policy** per entity type, in versions or in time, and its interaction with the ledger's never-reissue rule.
- **The full-state hash versus the Merkle layer** on tree-shaped payloads, resolved the way the device agent design resolves it, a subtree root standing in for the set hash, or not at all.
- **Order of work.** The parent edge with the one-head rule and the full-state hash first, since they fix lost updates today and need no deltas; the `Epoch` entity second; the mutation side table third, when the first consumer with a delta workload arrives.
